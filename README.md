# 不登校支援 AI 应用：技术路径与成品能力要求

## 1. 文档目的

本文档用于统一本项目的开发技术路线和产品能力边界，作为后续 Vibe Coding、代码审查、数据整理、功能验收和演示准备的共同基准。

本文档重点回答两个问题：

1. 使用什么技术、怎样组织代码和数据；
2. 最终成品必须能够做什么，以及明确不做什么。

---

## 2. 产品定位

### 2.1 一句话定义

> 面向不登校小中学生家长，通过 AI 对话整理需求，并依据限定、可追溯的机构与制度数据，筛选出实际可能利用的多个支援选项，同时说明费用、条件和判断依据的 Web 应用。

### 2.2 目标用户

- 不登校或存在持续缺席情况的小学生、中学生家长；
- 已经知道存在支援机构，但难以判断哪些机构真正适合自身现实条件的家长；
- 需要比较费用、补助、时间、学龄和通所条件的家长。

### 2.3 要解决的问题

现有行政门户主要解决“支援信息在哪里”的问题。本产品进一步解决：

> 候选机构已经存在，但家长无法判断哪些机构在制度、费用、时间和交通条件上真正可以利用。

本产品聚焦支援流程中的“接触—比较—选择”阶段，不尝试覆盖不登校问题的全部过程。

---

## 3. 技术路径

### 3.1 总体技术选择

| 层级 | 技术选择 | 作用 |
|---|---|---|
| 主语言 | TypeScript | 前端、API、规则计算统一使用一种语言 |
| 前端 | React + Vite | 实现咨询界面、追问流程和结果展示 |
| 后端 | Cloudflare Workers | 提供 AI、搜索、筛选和费用计算 API |
| AI | Microsoft Foundry 中已部署的模型接口 | 理解用户输入、提取条件、生成说明 |
| 数据校验 | Zod | 约束 AI 输出和 API 输入输出格式 |
| 初期数据 | JSON / CSV | 快速建立机构和补助制度数据 |
| 正式数据 | Cloudflare D1 | 存储和查询结构化机构、制度数据 |
| 测试 | Vitest | 验证资格判断、筛选和金额计算 |
| 部署 | Wrangler + Cloudflare Workers | 本地开发、预览和正式发布 |
| 代码管理 | Git / GitHub | 版本管理、备份和协作 |

### 3.2 为什么选择 TypeScript

- 与大会 Cloudflare Hands-on 和官方示例路线一致；
- Cloudflare Workers 和 D1 的支持成熟，并可通过标准 HTTPS API 调用 Microsoft Foundry；
- 前端与后端能够共享类型和数据结构；
- 类型检查有助于发现 AI 生成代码中的字段错误；
- AI 编码工具拥有大量 React、TypeScript、Cloudflare 相关示例；
- 避免依赖仍处于 Beta 阶段的 Cloudflare Python Workers；
- 部署和现场排错更容易参考官方资料。

本项目采用 Vibe Coding，TypeScript 代码主要由 AI 编码工具生成和维护。产品负责人主要维护提示词、数据、制度条件、产品文案和验收规则。

### 3.3 不使用 Agent 框架

本产品包含 AI 功能，但第一版不属于需要长期自主行动、计划任务或持续记忆的自主 Agent。

因此 MVP 不引入 Cloudflare Agents SDK，不实现复杂多 Agent、长期记忆、自主浏览或自主任务执行。

第一版采用普通、可控制的 AI 调用流程：

```text
用户输入
   ↓
AI 提取结构化条件
   ↓
TypeScript 规则引擎筛选与计算
   ↓
AI 根据已确认结果生成易懂说明
   ↓
显示多个候选方案
```

### 3.4 Microsoft Foundry 模型接入

本项目不使用 Cloudflare Workers AI 作为主要模型提供方，而是调用产品负责人已经在 Microsoft Foundry 中部署的模型接口。

模型调用必须由 Cloudflare Worker 后端发起。React 前端不得直接连接 Microsoft Foundry，也不得接触 API Key。

```text
React 前端
   ↓ 调用本项目 API
Cloudflare Worker
   ↓ 使用服务器端 Secret 调用
Microsoft Foundry 模型接口
```

Microsoft Foundry 在本项目中承担两类 AI 任务：

1. 将家长的自然语言描述转换为经过约束的结构化检索条件；
2. 根据规则引擎已经确认的候选结果，生成容易理解的说明和确认事项。

接入时需要确认以下非敏感配置：

- Microsoft Foundry Endpoint 类型；
- 模型 Deployment Name；
- API Version（若接口要求）；
- Foundry“查看代码 / Get code”页面提供的 REST 或 TypeScript 调用格式。

认证信息必须按以下方式管理：

- API Key 仅保存于 Cloudflare Secrets 或本地开发环境变量；
- API Key 不写入 React、HTML、TypeScript 源代码或 Git 仓库；
- 前端只调用本项目自己的 `/api/consult` 等后端接口；
- Endpoint、Deployment Name 和 API Version 使用环境变量管理；
- 不在应用日志中输出请求头、API Key 或完整模型请求内容。

建议使用的环境变量名称：

```text
MS_FOUNDRY_ENDPOINT
MS_FOUNDRY_DEPLOYMENT_NAME
MS_FOUNDRY_API_VERSION
MS_FOUNDRY_API_KEY
```

其中 `MS_FOUNDRY_API_KEY` 必须作为 Secret 管理，其余配置也不应由浏览器端直接读取。

### 3.5 第一版固定信息源

第一版不让 AI 自由搜索互联网，而是把允许使用的信息源写入白名单。当前先指定：

- 未来地図：https://miraitizu.com/

未来地図是面向不登校家庭的信息门户，包含家长会、Free School 等多种支援信息。它不是单一支援机构，因此系统需要从其中筛选符合指定地区和产品范围的条目，再整理为本项目自己的结构化数据。

第一版采用以下处理方式：

1. 在代码中固定允许的信息源域名与路径；
2. 人工确认未来地図中的目标机构页面；
3. 将机构名称、地区、对象学龄、费用、开放时间和原始链接等事实字段整理进本地 JSON；
4. AI 只能检索这份经过确认的数据，不能绕过白名单搜索开放互联网；
5. 每条结果必须显示原始页面链接和本项目的确认日期。

由于原网站内容受著作权保护，本项目不批量复制其介绍文章、图片或大段文字，只保存推荐所需的事实字段、简短摘要及来源链接。

建议在代码中固定如下来源注册表：

```ts
export const APPROVED_SOURCES = [
  {
    id: "miraitizu",
    origin: "https://miraitizu.com",
    allowedPaths: ["/parent-meeting/", "/freeschool/"],
  },
] as const;
```

后续增加信息源时，必须先将其加入白名单并完成字段与来源审查，不能由模型自行增加。

以下内容不应埋藏在 TypeScript 源代码中：

- AI 系统提示词：Markdown；
- 支援机构信息：JSON、CSV 或 D1；
- 补助制度与适用条件：JSON、CSV 或 D1；
- 来源 URL 与确认日期：数据字段；
- 页面文案和注意事项：独立文案文件；

## 5. AI、规则引擎与数据库的职责

### 5.1 AI 负责的工作

- 理解家长使用自然语言描述的情况；
- 从自由文本中提取检索所需条件；
- 发现必要条件缺失时，提出少量补充问题；
- 将确定性的检索和计算结果转换成容易理解的说明；
- 说明每个候选方案符合哪些条件；
- 提醒家长哪些信息需要向机构或自治体再次确认；
- 生成首次联系机构时可以询问的问题清单。

### 5.2 规则引擎负责的工作

- 判断机构是否接受相应学龄；
- 判断居住地或自治体资格是否满足；
- 判断开所日期、时间是否与用户条件相符；
- 判断交通与送迎条件是否符合；
- 计算东京都补助和区市町村追加补助；
- 计算预计实际自付金额；
- 记录候选被保留或排除的明确理由。

### 5.3 数据库负责的工作

- 保存机构名称、地址、学龄、开所时间和费用；
- 保存公营与民营机构类别；
- 保存自治体补助制度、金额、适用条件和来源；
- 保存数据来源 URL、确认日期和有效期；
- 为每条信息提供可追溯依据。

### 5.4 关键原则

> AI 不负责创造事实；AI 只理解用户、调用确定性工具，并解释数据库和规则引擎已经确认的结果。

本项目中的“AI”具体指 Microsoft Foundry 中已经部署的模型。模型只能接收完成当前任务所需的最少信息，不应收到孩子姓名、学校名称、详细地址等非必要个人信息。

### 5.5 第一版补助金计算规则（开发用假公式）

为了先完成端到端流程，第一版暂时使用以下开发用假公式：

```text
年度补助金 = 年收入 × 0.2
月度补助金 = 年度补助金 ÷ 12
预计月度自付金额 = max(0, 机构月费 - 月度补助金)
```

该公式只用于验证“用户输入 → 规则计算 → 结果展示”的程序流程，并非东京都、区市町村或任何真实制度的计算方法，也不能用于实际资格判断或申请。页面必须始终显示“开发演示用假公式（非真实制度）”。

计算必须由固定的 TypeScript 函数执行，Microsoft Foundry 只能解释结果，不得修改系数或自行计算金额。示例实现如下：

```ts
const PROTOTYPE_SUBSIDY_RATE = 0.2;

export function calculatePrototypeSubsidy(annualIncome: number) {
  if (!Number.isFinite(annualIncome) || annualIncome < 0) {
    throw new Error("annualIncome must be a non-negative number");
  }

  const annualSubsidy = Math.floor(
    annualIncome * PROTOTYPE_SUBSIDY_RATE,
  );

  return {
    annualSubsidy,
    monthlySubsidy: Math.floor(annualSubsidy / 12),
    formulaVersion: "prototype-v1",
    prototypeOnly: true,
  };
}
```

正式发布前必须用经过确认的真实制度规则替换此公式，并为每条规则补充制度名称、对象条件、金额上限、来源 URL、确认日期和规则版本。

## 6. 成品必须实现的能力

### 6.1 自然语言咨询

家长能够使用普通语言说明自身情况，不必一开始填写复杂表格。

示例：

> 我住在新宿区，孩子是初二，平日下午不愿意出门，我只能周末送他，每月最多能负担两万元。

### 6.2 条件结构化

AI 至少能够整理以下五项核心条件：

1. 居住区市町村；
2. 孩子的学年；
3. 可以利用的日期或时间；
4. 是否能够送迎；
5. 每月可以承担的金额。

结构化结果必须经过 Zod 校验，不能直接信任模型输出。

### 6.3 缺失信息追问

如果关键条件不足，AI 应提出必要的补充问题。追问应：

- 一次尽量不超过一个至两个问题；
- 不要求家长描述难以判断的心理状态；
- 优先询问可以客观回答的外形条件；
- 避免造成被诊断或被责备的感受。

### 6.4 支援机构检索

系统根据确认后的条件，从限定的数据集中搜索可能利用的机构。

第一版的机构数据来源固定为未来地図中经过人工确认并整理到本地的数据。AI 不进行开放网络搜索，也不推荐数据中不存在的机构。

第一版至少支持：

- 居住地区；
- 学龄；
- 公营／民营类别；
- 开所日期和时间；
- 基本费用；
- 送迎或通所条件。

### 6.5 制度资格筛选

系统根据规则排除明显不满足条件的机构或补助制度，并为排除结果保留理由。

例如：

- 对象学年不符；
- 仅限本区居民；
- 开所时间不符；
- 补助对象机构不符；
- 费用超过设定预算。

### 6.6 实际负担金额计算

系统结合以下信息计算预计自付金额：

- 机构费用；
- 东京都补助；
- 区市町村追加补助；
- 补助上限；
- 适用资格。

金额必须由 TypeScript 函数计算，不能由 LLM 自行心算。

计算结果必须标注为“预计”，并注明数据来源、确认日期和需要再次确认的条件。

在第一版开发阶段，先使用第 5.5 节的 `年收入 × 0.2` 假公式。此时结果必须额外标注为“开发演示值”，不得伪装成真实补助金额。

### 6.7 多个候选方案展示

系统不能只显示一个“最佳答案”。原则上应显示多个可能方案，并提供：

- 机构基本信息；
- 公营或民营类别；
- 符合条件的理由；
- 预计月费和自付金额；
- 适用的补助制度；
- 尚未确认的信息；
- 官方来源或机构页面链接；
- 首次咨询时建议确认的问题。

### 6.8 公营与民营并列

教育支援中心、校内支援空间等公营选项，应与民营 Free School 等选项并列展示，不能默认民营机构更优。

### 6.9 结果解释

AI 应使用容易理解、不过度确定的表达方式说明结果，例如：

- 为什么保留这些候选；
- 候选之间有什么现实差异；
- 哪些费用是估算值；
- 哪些资格需要向自治体确认；
- 家长下一步可以采取什么行动。

### 6.10 隐私保护

- 第一版原则上不要求登录；
- 不保存完整咨询对话；
- 不保存孩子姓名、学校名称等非必要信息；
- 不要求输入诊断信息；
- API 日志中不得记录完整敏感咨询内容；
- API 密钥必须存放在 Cloudflare Secrets 中；
- 页面明确说明输入内容的处理方式。
- 发送至 Microsoft Foundry 的内容应尽量匿名化和最小化；
- Cloudflare Worker 不得记录完整咨询文本或完整模型请求；
- 前端不得获取 Microsoft Foundry 的 Endpoint 认证信息或 API Key。

## 7. 成品明确不做的事情

### 7.1 不进行医学、心理或教育诊断

不得根据对话判断：

- 孩子属于哪种“不登校类型”；
- 是否患有某种心理或精神疾病；
- 不登校的单一原因；
- 是否需要特定治疗。

### 7.2 不预测复学

不得预测：

- 多久可以回到学校；
- 复学成功率；
- 选择某机构后是否一定复学。

学校复归不作为本产品唯一目标或 KPI。

### 7.3 不给出唯一正确答案

不得使用以下方式输出：

- “最适合您的机构只有这一家”；
- “AI 推荐第一名”；
- “选择其他机构是错误的”；
- 没有依据的排行榜或评分。

产品提供多个有依据的选择，最终决定权属于家长。

### 7.4 不使用模型知识虚构机构信息

AI 不得凭预训练知识或推测生成：

- 不在限定数据集中的机构；
- 未确认的费用；
- 未确认的补助金额；
- 未确认的空位；
- 未确认的资格条件；
- 虚构联系方式或营业时间。

### 7.5 不提供实时空位信息

除非未来获得机构侧实时数据，否则不得表示某机构当前“有空位”或“一定能够入所”。

### 7.6 不自动代替家长申请或联系

第一版不自动：

- 提交入所申请；
- 发送包含个人信息的邮件；
- 向学校或自治体提交材料；
- 预约面谈；
- 代表家长作出法律或教育决定。

### 7.7 不建立儿童社交或聊天空间

第一版不提供儿童之间的在线聊天室、社交匹配或在线居所功能，以避免隐私、安全和沟通风险。

### 7.8 不保存长期个人档案

第一版不建立儿童长期状态记录、出席记录或心理变化档案。

### 7.9 不代替专业人士

产品不能被描述为医生、心理师、学校、教育支援中心或行政机关的替代品。涉及安全、健康或紧急风险时，应引导用户联系相应专业机构。

### 7.10 不针对我们选定的区以外的区进行调查

初版只针对某一个特定的区的资源进行调查。

### 7.11 不搜索白名单以外的网站

第一版不进行开放互联网检索。即使模型知道其他机构或制度，也不得将其作为推荐结果。当前只使用未来地図中经过人工确认并录入本地数据集的条目。

## 8. 推荐结果的表达规范

### 8.1 应使用的表达

- “根据目前输入的条件，以下机构可能符合”；
- “预计实际负担金额”；
- “该条件仍需向机构确认”；
- “以下方案各有不同特点”；
- “最终选择由您和孩子共同决定”。

### 8.2 避免使用的表达

- “最优解”；
- “AI 判断您的孩子属于……”；
- “保证适合”；
- “一定可以获得补助”；
- “选择这家就能复学”；
- “不选择这家是错误的”。

## 9. 数据要求

每条机构或制度数据至少包含：

```json
{
  "id": "service-001",
  "name": "机构名称",
  "source_id": "miraitizu",
  "category": "public_or_private",
  "municipality": "新宿区",
  "eligible_grades": ["junior_high_1", "junior_high_2"],
  "opening_times": ["weekday_afternoon"],
  "monthly_fee": 30000,
  "source_url": "https://miraitizu.com/freeschool/example/",
  "verified_at": "2026-08-18",
  "notes": ["费用及名额需向机构确认"]
}
```

数据质量规则：

- `source_id` 必须存在于代码中的信息源白名单；
- `source_url` 的域名和路径必须符合该白名单；
- 必须保存来源 URL；
- 必须保存确认日期；
- 不确定信息使用 `null`，不得推测填充；
- 费用和制度数据必须区分“官方确认”“机构公开”“推算”；
- 过期数据不能继续作为确定事实展示；
- 计算规则必须能够追溯到具体制度条款。

第一版的 `miraitizu-resources.json` 只收录已选定区内、经过人工确认的机构。网页尚未明确给出的字段使用 `null`，由结果页面提示用户直接向机构确认。

## 10. MVP 优先级

### Rank A：必须完成

1. 用户输入基本条件；
2. AI 将自然语言转换为结构化条件；
3. 缺失条件追问；
4. 从限定数据中筛选机构；
5. 只使用未来地図白名单中人工整理的数据；
6. 制度条件判断；
7. 使用开发用假公式完成补助和预计自付金额计算；
8. 公营、民营多个候选并列展示；
9. 显示选择依据、来源和确认事项；
10. 输入内容不持久化；
11. 可公开访问的 Demo URL。

### Rank B：Rank A 稳定后再做

- 通所时间或交通可达范围判断；
- 出席扱い相关条件整理；
- 自动生成首次咨询问题清单；
- 更自然的多轮对话体验；
- D1 数据库和后台数据更新工具。

### 本次不做／仅作为未来构想

- 儿童聊天室；
- 不登校类型诊断；
- 复学时间或概率预测；
- 实时空位展示；
- 自动申请；
- 长期个人档案；
- 完整覆盖东京都所有区市町村。

## 11. 数据不足时的缩退方案

对于数据，也就是信息源，第一版先以未来地図为固定入口，并人为确认选定区内的机构页面。AI 实际检索的是已经整理到本地的结构化数据，而不是在运行时自由浏览网页。

| 问题 | 缩退方案 |
|---|---|
| 无法收集所有区市町村追加补助 | 只覆盖已经完整确认的区市町村 |
| 只能确认东京都统一补助 | 只计算东京都补助，并明确不含区市町村追加补助 |
| 无法取得机构费用 | 让用户输入月费，只提供补助计算功能 |
| 机构数据无法批量取得 | 限定 1～2 个区，手工建立完整数据集 |
| 未来地図页面字段不完整 | 缺失字段使用 `null`，保留来源链接并提示向机构确认 |
| AI 结构化输出不稳定 | 退回五项固定表单输入 |
| AI 服务不可用 | 保留普通条件筛选与费用计算功能 |

缩退后仍必须保留的核心价值是：

> 根据现实条件减少候选范围，并提供可追溯的费用和制度判断材料。

## 13. Vibe Coding 开发约束

向 AI 编码工具下达任务时，必须持续遵守以下约束：

1. 不允许把资格和金额判断完全交给 LLM；
2. 不允许 AI 生成数据库中不存在的机构；
3. 不允许把提示词、业务规则和机构数据全部写进一个文件；
4. 每项核心规则都必须有自动测试；
5. 每个 API 输入输出必须有 Zod Schema；
6. 制度和机构数据必须包含来源及确认日期；
7. 不默认保存用户对话；
8. 新增功能不得突破“明确不做”的边界；
9. 优先保证 Rank A 完整，不因新增功能破坏主流程；
10. 所有页面文案应避免诊断、保证和唯一推荐措辞；
11. Microsoft Foundry 调用必须统一经过 `foundryClient.ts`；
12. Foundry API Key 只能使用 Cloudflare Secret 或本地环境变量；
13. 不得将完整敏感咨询内容写入日志、数据库或错误追踪系统；
14. 发送给 Foundry 的字段必须遵守最少必要原则；
15. 模型响应不得绕过 Zod 校验直接参与机构筛选或金额计算。
16. AI 不得在运行时搜索白名单以外的网站；
17. 新增信息源前必须更新 `sourceRegistry.ts` 并完成数据审查；
18. 不得批量复制未来地図的介绍文章、图片或大段文字；
19. `prototype-v1` 假公式只能用于开发演示，不能被描述为真实补助制度；
20. 补助系数、上限和资格条件不得由模型生成或修改。

# 不登校支援 AI アプリ：技術方針と成果物の機能要件（日本語版）

## 1. 文書の目的

本書は、本プロジェクトの開発技術方針とプロダクトの機能範囲を統一し、今後の Vibe Coding、コードレビュー、データ整理、機能検収およびデモ準備における共通基準とするためのものです。

本書では、主に次の二つの問いに答えます。

1. どの技術を使用し、コードとデータをどのように構成するか。
2. 最終成果物が必ず実現すべきことと、明確に実施しないことは何か。

---

## 2. プロダクトの位置付け

### 2.1 一文での定義

> 不登校の小中学生の保護者を対象に、AI との対話を通じてニーズを整理し、限定された追跡可能な支援機関・制度データに基づいて、実際に利用できる可能性のある複数の支援先を絞り込み、費用・条件・判断根拠を提示する Web アプリケーション。

### 2.2 対象ユーザー

- 不登校、または継続的な欠席状態にある小中学生の保護者。
- 支援機関の存在は知っているが、自分たちの現実的な条件に合う機関を判断することが難しい保護者。
- 費用、助成、時間、対象学齢、通所条件を比較する必要がある保護者。

### 2.3 解決する課題

既存の行政ポータルは、主に「支援情報がどこにあるか」という問題を解決しています。本プロダクトは、さらに次の問題を解決します。

> 支援先の候補は存在していても、制度、費用、時間、交通条件を踏まえたときに、保護者が実際に利用できる機関を判断できない。

本プロダクトは、支援プロセスにおける「接触―比較―選択」の段階に焦点を当て、不登校に関するすべての課題を網羅するものではありません。

---

## 3. 技術方針

### 3.1 全体的な技術選定

| レイヤー | 採用技術 | 役割 |
|---|---|---|
| メイン言語 | TypeScript | フロントエンド、API、ルール計算を一つの言語に統一 |
| フロントエンド | React + Vite | 相談画面、追加質問フロー、結果表示を実装 |
| バックエンド | Cloudflare Workers | AI、検索、絞り込み、費用計算 API を提供 |
| AI | Microsoft Foundry にデプロイ済みのモデル API | ユーザー入力の理解、条件抽出、説明生成 |
| データ検証 | Zod | AI 出力および API 入出力の形式を制約 |
| 初期データ | JSON / CSV | 支援機関および助成制度データを迅速に構築 |
| 正式データ | Cloudflare D1 | 構造化された支援機関・制度データを保存、検索 |
| テスト | Vitest | 資格判定、絞り込み、金額計算を検証 |
| デプロイ | Wrangler + Cloudflare Workers | ローカル開発、プレビュー、本番公開 |
| コード管理 | Git / GitHub | バージョン管理、バックアップ、共同作業 |

### 3.2 TypeScript を選択する理由

- 大会の Cloudflare Hands-on および公式サンプルの方針と一致する。
- Cloudflare Workers と D1 のサポートが成熟しており、標準 HTTPS API で Microsoft Foundry を呼び出せる。
- フロントエンドとバックエンドで型およびデータ構造を共有できる。
- 型チェックにより、AI が生成したコードのフィールド誤りを発見しやすい。
- AI コーディングツールには React、TypeScript、Cloudflare に関する豊富な事例がある。
- まだ Beta 段階にある Cloudflare Python Workers への依存を避けられる。
- デプロイや現場でのトラブル対応において、公式資料を参照しやすい。

本プロジェクトでは Vibe Coding を採用し、TypeScript コードは主に AI コーディングツールで生成・保守します。プロダクト責任者は主に、プロンプト、データ、制度条件、プロダクト文言および検収ルールを管理します。

### 3.3 Agent フレームワークを使用しない

本プロダクトは AI 機能を含みますが、第一版では長期的な自律行動、タスク計画、継続的な記憶を必要とする自律型 Agent には該当しません。

そのため MVP では Cloudflare Agents SDK を導入せず、複雑なマルチ Agent、長期記憶、自律ブラウジング、自律的なタスク実行を実装しません。

第一版では、通常の制御可能な AI 呼び出しフローを採用します。

```text
ユーザー入力
   ↓
AI が構造化条件を抽出
   ↓
TypeScript のルールエンジンが絞り込みと計算を実行
   ↓
AI が確認済みの結果を分かりやすく説明
   ↓
複数の候補を表示
```

### 3.4 Microsoft Foundry モデルとの接続

本プロジェクトでは Cloudflare Workers AI を主要モデルプロバイダーとして使用せず、プロダクト責任者が Microsoft Foundry にデプロイ済みのモデル API を呼び出します。

モデルは Cloudflare Worker のバックエンドから呼び出します。React フロントエンドから Microsoft Foundry に直接接続してはならず、API Key をフロントエンドに渡してはいけません。

```text
React フロントエンド
   ↓ 本プロジェクトの API を呼び出す
Cloudflare Worker
   ↓ サーバー側の Secret を使用して呼び出す
Microsoft Foundry モデル API
```

Microsoft Foundry は、本プロジェクトで次の二種類の AI タスクを担当します。

1. 保護者の自然言語による説明を、制約された構造化検索条件へ変換する。
2. ルールエンジンで確認済みの候補結果を、分かりやすい説明と確認事項に変換する。

接続時には、次の機密情報ではない設定を確認する必要があります。

- Microsoft Foundry Endpoint の種類。
- モデルの Deployment Name。
- API Version（API が要求する場合）。
- Foundry の「コードの表示 / Get code」画面に示される REST または TypeScript の呼び出し形式。

認証情報は、次の方法で管理しなければなりません。

- API Key は Cloudflare Secrets またはローカル開発用環境変数にのみ保存する。
- API Key を React、HTML、TypeScript のソースコードや Git リポジトリに書き込まない。
- フロントエンドは、本プロジェクトの `/api/consult` などのバックエンド API のみを呼び出す。
- Endpoint、Deployment Name、API Version は環境変数で管理する。
- リクエストヘッダー、API Key、モデルへの完全なリクエスト内容をアプリケーションログへ出力しない。

推奨する環境変数名：

```text
MS_FOUNDRY_ENDPOINT
MS_FOUNDRY_DEPLOYMENT_NAME
MS_FOUNDRY_API_VERSION
MS_FOUNDRY_API_KEY
```

`MS_FOUNDRY_API_KEY` は必ず Secret として管理し、その他の設定もブラウザ側から直接読み取れないようにします。

### 3.5 第一版の固定情報源

第一版では AI にインターネットを自由検索させず、利用可能な情報源をホワイトリストとしてコードに固定します。現時点では次のサイトを指定します。

- 未来地図：https://miraitizu.com/

未来地図は、不登校家庭向けに親の会、フリースクールなど多様な支援情報を掲載するポータルです。単一の支援機関ではないため、サイト内から対象地域とプロダクトの範囲に合う情報を選び、本プロジェクト独自の構造化データとして整理する必要があります。

第一版では、次の方法で処理します。

1. 利用を許可する情報源のドメインとパスをコードに固定する。
2. 未来地図内の対象機関ページを人手で確認する。
3. 機関名、地域、対象学齢、費用、開所時間、元ページのリンクなどの事実フィールドをローカル JSON に整理する。
4. AI は確認済みデータのみを検索し、ホワイトリストを回避してオープンなインターネットを検索してはならない。
5. 各結果に元ページへのリンクと本プロジェクトでの確認日を表示する。

元サイトのコンテンツは著作権で保護されているため、紹介記事、画像、長文を一括転載せず、推薦に必要な事実フィールド、短い要約、情報源リンクのみを保存します。

コードでは、次のような情報源レジストリを固定します。

```ts
export const APPROVED_SOURCES = [
  {
    id: "miraitizu",
    origin: "https://miraitizu.com",
    allowedPaths: ["/parent-meeting/", "/freeschool/"],
  },
] as const;
```

今後情報源を追加する場合は、事前にホワイトリストへ登録し、フィールドと情報源の審査を完了しなければなりません。モデルが自ら情報源を追加することは禁止します。

## 4. システム構成

### 4.1 論理構成

```text
┌──────────────────────────────────┐
│ React ユーザーインターフェース   │
│ 相談入力／追加質問／候補結果      │
└────────────────┬─────────────────┘
                 │ HTTPS
┌────────────────▼─────────────────┐
│ Cloudflare Worker API            │
│                                  │
│ 1. 入力検証                      │
│ 2. AI による条件抽出             │
│ 3. 不足条件の判定                │
│ 4. 支援機関検索                  │
│ 5. 資格・費用計算                │
│ 6. AI による結果説明             │
└──────────────┬───────────┬───────┘
               │           │
       ┌───────▼──────┐ ┌──▼──────────────────┐
       │ MS Foundry   │ │ JSON / D1           │
       │ 理解と説明   │ │ ホワイトリスト化した │
       │              │ │ 機関・制度データ      │
       └──────────────┘ └─────────────────────┘
```

### 4.2 推奨ディレクトリ構成


### 4.3 プロダクト責任者が直接管理できる内容

次の内容は TypeScript のソースコード内に埋め込まないものとします。

- AI のシステムプロンプト：Markdown。
- 支援機関情報：JSON、CSV または D1。
- 助成制度と適用条件：JSON、CSV または D1。
- 情報源 URL と確認日：データフィールド。
- ページ文言と注意事項：独立した文言ファイル。
- デモ用テストケース：JSON。
- プロダクトルールの説明：Markdown。

Microsoft Foundry のモデル接続コードは `foundryClient.ts` に集約します。他のモジュールで Endpoint、認証ヘッダー、モデルリクエストを個別に組み立ててはなりません。審査が難しい複数の接続箇所を作らないためです。

情報源ホワイトリストは `sourceRegistry.ts` で一元管理します。未来地図から人手で確認した支援機関情報は `miraitizu-resources.json` に整理し、AI が未審査の Web ページを直接読み取らないようにします。

## 5. AI、ルールエンジン、データベースの役割

### 5.1 AI が担当すること

- 保護者が自然な言葉で説明した状況を理解する。
- 自由記述から検索に必要な条件を抽出する。
- 必要条件が不足している場合、少数の追加質問を行う。
- 確定的な検索・計算結果を分かりやすい説明へ変換する。
- 各候補がどの条件に合っているかを説明する。
- 機関または自治体へ再確認すべき情報を案内する。
- 初回問い合わせ時に確認できる質問リストを作成する。

### 5.2 ルールエンジンが担当すること

- 機関が該当する学齢を受け入れているか判定する。
- 居住地または自治体の利用資格を満たすか判定する。
- 開所日・時間がユーザー条件に合うか判定する。
- 交通・送迎条件が合うか判定する。
- 東京都の助成および区市町村の追加助成を計算する。
- 予想される実質自己負担額を計算する。
- 候補を残した理由、除外した理由を明示的に記録する。

### 5.3 データベースが担当すること

- 機関名、住所、対象学齢、開所時間、費用を保存する。
- 公営・民営の機関区分を保存する。
- 自治体の助成制度、金額、適用条件、情報源を保存する。
- 情報源 URL、確認日、有効期限を保存する。
- 各情報について追跡可能な根拠を提供する。

### 5.4 重要原則

> AI は事実を作らない。AI はユーザーを理解し、確定的なツールを呼び出し、データベースとルールエンジンで確認済みの結果だけを説明する。

本プロジェクトにおける「AI」とは、Microsoft Foundry にデプロイ済みのモデルを指します。モデルには現在のタスクに必要な最小限の情報のみを送信し、子どもの氏名、学校名、詳細住所など、不要な個人情報を送ってはなりません。

### 5.5 第一版の助成金計算ルール（開発用の仮計算式）

まず一連の処理を完成させるため、第一版では次の開発用仮計算式を使用します。

```text
年間助成金 = 年収 × 0.2
月額助成金 = 年間助成金 ÷ 12
月額自己負担見込額 = max(0, 機関の月額費用 - 月額助成金)
```

この計算式は、「ユーザー入力 → ルール計算 → 結果表示」というプログラムの流れを検証するためだけのものです。東京都、区市町村、その他いかなる実在制度の計算方法でもなく、実際の資格判定や申請には使用できません。画面には常に「開発デモ用の仮計算式（実在制度ではありません）」と表示します。

計算は固定された TypeScript 関数で実行し、Microsoft Foundry は結果の説明のみを行います。モデルが係数を変更したり、自ら金額を計算したりしてはなりません。実装例は次のとおりです。

```ts
const PROTOTYPE_SUBSIDY_RATE = 0.2;

export function calculatePrototypeSubsidy(annualIncome: number) {
  if (!Number.isFinite(annualIncome) || annualIncome < 0) {
    throw new Error("annualIncome must be a non-negative number");
  }

  const annualSubsidy = Math.floor(
    annualIncome * PROTOTYPE_SUBSIDY_RATE,
  );

  return {
    annualSubsidy,
    monthlySubsidy: Math.floor(annualSubsidy / 12),
    formulaVersion: "prototype-v1",
    prototypeOnly: true,
  };
}
```

正式公開前に、確認済みの実在制度のルールへ置き換える必要があります。また、各ルールに制度名、対象条件、金額上限、情報源 URL、確認日、ルールバージョンを追加します。

## 6. 成果物が必ず実現する機能

### 6.1 自然言語による相談

保護者は、最初から複雑なフォームを入力することなく、普段の言葉で状況を説明できます。

例：

> 新宿区に住んでいます。子どもは中学2年生で、平日の午後は外出したがりません。私が送迎できるのは週末だけで、毎月負担できるのは2万円までです。

### 6.2 条件の構造化

AI は、少なくとも次の五つの基本条件を整理できるものとします。

1. 居住する区市町村。
2. 子どもの学年。
3. 利用可能な曜日または時間。
4. 送迎の可否。
5. 毎月負担できる金額。

構造化結果は必ず Zod で検証し、モデル出力をそのまま信用してはなりません。

### 6.3 不足情報への追加質問

重要な条件が不足している場合、AI は必要な追加質問を行います。質問は次の条件を満たすものとします。

- 一度に一～二問以内を目安とする。
- 保護者が判断しにくい心理状態を説明させない。
- 客観的に答えられる外形的条件を優先する。
- 診断された、または責められたと感じさせない。

### 6.4 支援機関の検索

システムは、確認済みの条件に基づいて、限定されたデータセットから利用できる可能性のある機関を検索します。

第一版の機関データは、未来地図から人手で確認し、ローカルに整理したものに限定します。AI はオープンなインターネットを検索せず、データ内に存在しない機関を推薦しません。

第一版では、少なくとも次の条件を扱います。

- 居住地域。
- 対象学齢。
- 公営／民営の区分。
- 開所日と時間。
- 基本費用。
- 送迎または通所条件。

### 6.5 制度資格による絞り込み

システムは、ルールに基づいて明らかに条件を満たさない機関または助成制度を除外し、除外理由を保持します。

例：

- 対象学年が一致しない。
- 当該区の住民に限定されている。
- 開所時間が合わない。
- 助成対象機関に該当しない。
- 費用が設定予算を超えている。

### 6.6 実質負担額の計算

システムは、次の情報を組み合わせて自己負担見込額を計算します。

- 機関の利用費用。
- 東京都の助成。
- 区市町村の追加助成。
- 助成上限。
- 適用資格。

金額は TypeScript 関数で計算し、LLM に暗算させてはなりません。

計算結果には「見込額」であることを明記し、情報源、確認日、再確認が必要な条件を表示します。

第一版の開発段階では、第 5.5 節の `年収 × 0.2` という仮計算式を使用します。この場合、結果に「開発デモ用の値」と追加表示し、実在する助成金額のように見せてはなりません。

### 6.7 複数候補の表示

システムは、一つの「最適解」だけを表示してはなりません。原則として複数の候補を表示し、次の情報を提供します。

- 機関の基本情報。
- 公営・民営の区分。
- 条件に合う理由。
- 月額費用および自己負担見込額。
- 適用可能な助成制度。
- 未確認の情報。
- 公式情報源または機関ページへのリンク。
- 初回相談時に確認することを推奨する質問。

### 6.8 公営と民営を並列表示

教育支援センター、校内支援スペースなどの公営の選択肢を、民営のフリースクールなどと並列に表示します。民営機関を初期設定で優位に扱ってはなりません。

### 6.9 結果の説明

AI は、分かりやすく断定しすぎない表現で結果を説明します。例えば、次の内容です。

- なぜこれらの候補を残したのか。
- 候補間にどのような現実的な違いがあるか。
- どの費用が見込額なのか。
- どの資格を自治体に確認する必要があるか。
- 保護者が次にどのような行動を取れるか。

### 6.10 プライバシー保護

- 第一版では原則としてログインを要求しない。
- 相談内容の全文を保存しない。
- 子どもの氏名、学校名など不要な情報を保存しない。
- 診断情報の入力を要求しない。
- API ログに機微な相談内容の全文を記録しない。
- API Key は Cloudflare Secrets に保存する。
- 入力内容の処理方法を画面上で明示する。
- Microsoft Foundry へ送る内容は、可能な限り匿名化・最小化する。
- Cloudflare Worker は相談テキスト全文やモデルリクエスト全文を記録しない。
- フロントエンドは Microsoft Foundry の Endpoint 認証情報や API Key を取得できないようにする。

## 7. 成果物で明確に実施しないこと

### 7.1 医学・心理・教育上の診断を行わない

対話内容から次のことを判断してはなりません。

- 子どもがどの「不登校タイプ」に当てはまるか。
- 心理疾患または精神疾患があるか。
- 不登校の原因が何かを一つに特定すること。
- 特定の治療が必要か。

### 7.2 復学を予測しない

次のことを予測してはなりません。

- いつ学校に戻れるか。
- 復学の成功率。
- 特定の機関を選べば必ず復学できるか。

学校復帰を、本プロダクトの唯一の目標または KPI としません。

### 7.3 唯一の正解を提示しない

次のような出力は禁止します。

- 「あなたに最適な機関はここだけです」。
- 「AI 推薦ランキング第1位」。
- 「ほかの機関を選ぶのは誤りです」。
- 根拠のないランキングや採点。

本プロダクトは根拠のある複数の選択肢を提示し、最終決定は保護者に委ねます。

### 7.4 モデル知識で機関情報を捏造しない

AI は、事前学習知識や推測に基づいて次の情報を生成してはなりません。

- 限定データセットに存在しない機関。
- 未確認の費用。
- 未確認の助成金額。
- 未確認の空き状況。
- 未確認の資格条件。
- 架空の連絡先または営業時間。

### 7.5 リアルタイムの空き状況を提供しない

将来、機関側からリアルタイムデータを取得できるようになるまでは、特定の機関に現在「空きがある」「必ず入所できる」と表示してはなりません。

### 7.6 保護者の代わりに申請・連絡しない

第一版では、次の処理を自動化しません。

- 入所申請の提出。
- 個人情報を含むメールの送信。
- 学校または自治体への書類提出。
- 面談予約。
- 保護者に代わる法的または教育上の決定。

### 7.7 子ども向け交流・チャット空間を作らない

第一版では、プライバシー、安全、コミュニケーション上のリスクを避けるため、子ども同士のオンラインチャット、ソーシャルマッチング、オンライン上の居場所機能を提供しません。

### 7.8 長期的な個人記録を保存しない

第一版では、子どもの長期的な状態記録、出席記録、心理変化の記録を作成しません。

### 7.9 専門家の代替にならない

本プロダクトを、医師、心理士、学校、教育支援センター、行政機関の代替として説明してはなりません。安全、健康、緊急性に関わるリスクがある場合は、該当する専門機関への相談を案内します。

### 7.10 選定した区以外を調査対象にしない

第一版では、特定の一つの区にある支援資源のみを調査対象とします。

### 7.11 ホワイトリスト外の Web サイトを検索しない

第一版では、オープンなインターネット検索を行いません。モデルが他の機関や制度を知っていても、推薦結果に含めてはなりません。現時点では、未来地図から人手で確認してローカルデータセットへ登録した項目だけを利用します。

## 9. データ要件

各機関または制度のデータには、少なくとも次の項目を含めます。

```json
{
  "id": "service-001",
  "name": "機関名",
  "source_id": "miraitizu",
  "category": "public_or_private",
  "municipality": "新宿区",
  "eligible_grades": ["junior_high_1", "junior_high_2"],
  "opening_times": ["weekday_afternoon"],
  "monthly_fee": 30000,
  "source_url": "https://miraitizu.com/freeschool/example/",
  "verified_at": "2026-08-18",
  "notes": ["費用および空き状況は機関への確認が必要"]
}
```

データ品質ルール：

- `source_id` は、コード内の情報源ホワイトリストに存在しなければならない。
- `source_url` のドメインとパスは、ホワイトリストの条件に一致しなければならない。
- 情報源 URL を必ず保存する。
- 確認日を必ず保存する。
- 不明な情報には `null` を使用し、推測で補完しない。
- 費用・制度データは、「公式確認済み」「機関公開情報」「推算」を区別する。
- 期限切れのデータを確定的な事実として表示し続けない。
- 計算ルールから具体的な制度条文を追跡できるようにする。

第一版の `miraitizu-resources.json` には、選定した区内にあり、人手で確認した機関のみを登録します。Web ページに明記されていないフィールドには `null` を設定し、結果画面で機関への直接確認を案内します。

## 11. データ不足時の縮退方針

第一版では、未来地図を固定の情報入口とし、選定した区内の機関ページを人手で確認します。AI が実際に検索するのはローカルに整理した構造化データであり、実行時に Web ページを自由閲覧するものではありません。

| 問題 | 縮退方法 |
|---|---|
| 区市町村の追加助成をすべて収集できない | 完全に確認できた区市町村だけを対象にする |
| 東京都共通の助成しか確認できない | 東京都の助成だけを計算し、区市町村の追加助成を含まないことを明示する |
| 機関の費用を取得できない | ユーザーに月額費用を入力してもらい、助成計算機能だけを提供する |
| 機関データを一括取得できない | 対象を一～二区に限定し、人手で完全なデータセットを作る |
| 未来地図のページで必要項目が不足している | 不足項目を `null` とし、情報源リンクを残して機関への確認を案内する |
| AI の構造化出力が不安定 | 五つの固定フォーム入力へ切り替える |
| AI サービスを利用できない | 通常の条件絞り込みと費用計算機能を維持する |

縮退後も、次の中核価値を維持しなければなりません。

> 現実的な条件に基づいて候補を減らし、追跡可能な費用・制度判断の材料を提供する。

## 12. 検収基準

次の条件を満たした場合に、MVP が完成したものとします。

### 機能検収

- [ ] 保護者が自然言語で状況を入力できる。
- [ ] AI が五つの基本条件を抽出できる。
- [ ] 必須情報が不足している場合、検索を開始しない。
- [ ] システムが限定データセットだけを検索する。
- [ ] 現在の情報源は、未来地図のホワイトリストおよび許可されたパスだけである。
- [ ] 推薦結果の機関は、人手で整理したローカルデータ内に存在する。
- [ ] 地域、学齢、時間、予算に基づいて絞り込める。
- [ ] 費用計算を確定的な関数で実行する。

## 13. Vibe Coding の開発制約

AI コーディングツールへタスクを依頼する際は、常に次の制約を守ります。

1. 資格判定と金額判定を LLM だけに任せない。
2. AI がデータベースに存在しない機関を生成することを禁止する。
3. プロンプト、業務ルール、機関データを一つのファイルへまとめない。
4. 各中核ルールに自動テストを用意する。
5. すべての API 入出力に Zod Schema を定義する。
6. 制度・機関データに情報源と確認日を含める。
7. ユーザーとの対話を標準で保存しない。
8. 新機能によって「明確に実施しないこと」の境界を越えない。
9. Rank A の完成を優先し、新機能によって主要フローを壊さない。
10. すべての画面文言で、診断、保証、唯一の推薦に当たる表現を避ける。
11. Microsoft Foundry の呼び出しを必ず `foundryClient.ts` に集約する。
12. Foundry API Key は Cloudflare Secret またはローカル環境変数だけで管理する。
13. 機微な相談内容の全文をログ、データベース、エラー追跡システムへ保存しない。
14. Foundry へ送信するフィールドは、必要最小限の原則を守る。
15. モデルの応答を Zod で検証せずに、機関の絞り込みや金額計算へ使用しない。
16. AI が実行時にホワイトリスト外の Web サイトを検索することを禁止する。
17. 情報源を追加する前に `sourceRegistry.ts` を更新し、データ審査を完了する。
18. 未来地図の紹介記事、画像、長文を一括転載しない。
19. `prototype-v1` の仮計算式は開発デモにのみ使用し、実在の助成制度として説明しない。
20. 助成係数、上限、資格条件をモデルに生成・変更させない。

## 14. 最終的なプロダクト定義

> 本プロダクトは、保護者に代わって判断する診断システムやランキングシステムではなく、AI を活用した支援先選択ツールです。対話を通じて保護者が答えられる現実的な条件を整理し、ホワイトリスト化した情報源から人手で確認したデータを検索し、確定的なルールで制度と費用を判定します。そのうえで、複数の選択肢と根拠を分かりやすく提示し、保護者がより安心して最初の問い合わせへ進めるよう支援します。第一版の助成計算式は、処理フローの開発にのみ使用する仮ルールであり、正式利用前に追跡可能な実在制度のルールへ置き換える必要があります。
